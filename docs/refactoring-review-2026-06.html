1.요약 (Executive Summary)

이 프로젝트는 한국 보통주/우선주 괴리율을 추적하는 정적 대시보드로, GitHub Actions가 데이터를 수집해 저장소에 커밋하고 GitHub Pages가 그대로 서빙하는 "서버리스 + 저장소 = DB" 구조입니다. 외부 프레임워크·차트 라이브러리·빌드 도구 없이 순수 HTML/CSS/JS + Python 표준 구성으로 만들어져 있고, 다중 데이터 소스 폴백, 주·야간 선물 세션 처리, 발행사 단위 sqrt 시총가중 지수 등 도메인 로직의 완성도는 상당히 높습니다.

반면 성장 과정에서 누적된 구조적 부채가 명확합니다. 핵심은 네 가지입니다: (1) 백필된 과거 데이터가 실제로 유실된 상태(재발 가능한 파이프라인 결함), (2) 42.5MB짜리 data.js를 매 방문마다 캐시 무효화 상태로 전송, (3) 4,884줄 단일 index.html / 1,800~2,000줄 단일 Python 스크립트 모놀리스 + 동일 로직의 Python/JS 이중 구현, (4) 테스트 0개·의존성 미고정 상태에서 매일 자동으로 데이터를 덮어쓰는 운영 방식입니다.

지금 당장 확인이 필요한 사실 (검증 완료): proxy_backfill_progress.json에는 삼성전자 히스토리가 1989-09-25, CJ4우선(전환)이 2019-08-09까지 백필 완료된 것으로 기록되어 있으나, 현재 data.js의 실제 시작일은 각각 1996-06-25, 2021-02-08입니다. 즉 어렵게 백필한 과거 구간이 이후의 전체 재수집 과정에서 이미 소실되었습니다. 원인 경로는 이슈 C1 참고. 외부 소스(프록시 API)에 원본이 남아있을 때 재백필 + 스냅샷 백업 체계를 먼저 갖추는 것을 최우선으로 권고합니다.

잘 되어 있는 점

  • 의존성 제로 프런트엔드 — 프레임워크/차트 라이브러리 없이 캔버스 직접 렌더링. 빌드 단계가 없어 배포가 단순하고 빠릅니다.
  • 다층 데이터 소스 폴백 — 내부 API → KIS(한투) → 네이버 → 이전 스냅샷 순의 우아한 성능 저하(graceful degradation)가 수집기 전반에 일관되게 구현됨.
  • 세심한 시장 도메인 처리 — KST 주간/야간 선물 세션 판별, 거래정지일(volume=0) 제외, Yahoo 소급조정 오류 필터(괴리율 < −100% 제거), 백필 시 가격 조정비율 안전범위(0.01~10x) 검증 등.
  • UX 디테일 — 다크/라이트 테마, iframe 임베드 모드, URL 상태 공유(?code=), 줌 패널, 스파크라인, 모달 포커스 관리, escapeHtml 기반 XSS 방어.
  • analysis/ 의 통계적 엄밀성 — 클러스터 부트스트랩, BH FDR 보정, 단측검정 해석 주의사항까지 명시한 이벤트 스터디와 현실적 가정(수수료·정수주식·배당 재투자)의 백테스트.

핵심 권고 (한 줄씩)

  1. Phase 0 (즉시): 데이터 스냅샷 백업 + 백필 소실 경로 수정 + 의존성 고정 + 워크플로우 동시성 제어. 코드 구조는 건드리지 않고 안전망부터.
  2. Phase 1: data.js를 "메타+현재가(소형) / 종목별 히스토리(지연 로드)"로 분리해 초기 전송량을 42.5MB → 수백 KB로.
  3. Phase 2: index.html을 ES 모듈로 분해(빌드 도구 없이 가능), 상태-렌더 분리.
  4. Phase 3: Python을 소스 어댑터 패키지로 재구성 + pytest 회귀 테스트, 지수 산정 방식 단일화.
  5. holding_value: 분석·리팩토링은 별도 세션에서 진행하되, 공통 모듈 추출까지 갈 경우 두 저장소를 함께 연결한 세션에서. (7장)

3.컴포넌트별 품질 평가

index.html — 대시보드 구조 C / 기능 A

  • 강점 시간축 기반 차트 스케일(거래일 공백을 실제 시간 간격으로 표현, gap 분절 처리), 줌 오버뷰 패널, SMA250/EMA 오버레이, 베타·상관계수 계산, 테이블 정렬, autofit 텍스트 등 기능 밀도가 높음. 순수 함수(계산/포맷)들은 품질이 좋아 추출만 하면 바로 테스트 가능.
  • 약점 약 3,440줄 JS가 하나의 IIFE 안에 ~110개 함수로 존재. 모듈 경계가 없고 상태가 10여 개의 최상위 let으로 산재(selectedIdx, zoomWindow, todayOverviewData, latestMarketExtras…). 모든 렌더 함수가 innerHTML 전체 재생성 + 리스너 재바인딩 방식이라 스냅샷 적용(5분마다)마다 DOM 전체가 교체됨.
  • 약점 "지수/평균"이 세 가지 정의로 공존: ① data.js의 일별 sqrt 시총가중 지수(fetch_data.py), ② 프런트 실시간 sqrt 지수(calculateSqrtPreferredMarketCapSpreadIndex), ③ current.json의 대표종목 단순평균(build_summary). 이로 인한 실제 불일치는 이슈 H4 참고.
  • 사소 renderChart 내 사용되지 않는 잔존 코드(renderChart._raf/_lastCtx, index.html:3263~3266), 기간 필터의 UTC 기준 날짜 컷오프(index.html:3653), 일반 카드의 키보드 포커스 불가(avg 카드만 tabindex), 캔버스 툴팁이 mousemove 전용이라 모바일 터치 미지원.

fetch_data.py — 일별 파이프라인 구조 C+ / 견고성 B−

  • 강점 증분 갱신(마지막 날짜−5일 중첩 재수집), 외부 백필 시 중첩 구간 중앙값 비율로 가격 스케일 보정 + 안전범위 밖이면 스킵, 거래정지일 제외, 발행사 단위 지수 산출(휴장일 오염 방지용 "종목 수 절반 미만" 필터) 등 데이터 위생 처리가 좋음.
  • 약점 신규 종목 추가 시 전체를 버리고 재다운로드하는 경로에서 백필 이력이 보존되지 않음 → 실데이터 유실 확인 (이슈 C1).
  • 약점 모듈 수준 가변 캐시 dict 11개 + import 시점에 config 로드(PAIRS) → 단위 테스트가 사실상 불가능한 구조. 수집(transport)·파싱·병합·지수 계산·CLI가 한 파일.
  • 약점 사설 엔드포인트 기본값 하드코딩(이슈 H1). yfinance .info를 티커별 순차 호출(느리고 자주 깨지는 API). CI에서는 내부 API가 항상 실패해 매 실행마다 불필요한 타임아웃/경고 발생.

fetch_current.py — 장중 파이프라인 구조 B− / 견고성 B+

  • 강점 세 파일 중 가장 정돈됨. 원자적 파일 쓰기(tmp→replace), 토큰 캐시(파일+락+만료 마진), 폴백 체인이 명시적, 이전 스냅샷 보존 규칙(선물 메트릭 세션/신선도 검사)이 꼼꼼함.
  • 약점 ssl._create_default_https_context = ssl._create_unverified_context 전역 패치(1610행) — CME 마스터 파일 하나 받자고 프로세스 전체 TLS 검증을 끔.
  • 약점 KIS 야간선물 후보 코드 생성(build_kospi200_night_future_keys)의 매직 코드 나열(101W09 등), 외부 사이트 HTML 정규식 파싱 2종 — 깨지기 쉬운 의존이며 동일 로직이 JS에도 중복.

admin.html / workflows / analysis

  • admin.html 보안 — fine-grained PAT를 localStorage에 평문 저장(297행). 같은 오리진에서 XSS 한 번이면 저장소 쓰기 권한 토큰이 유출됨. triggerWorkflow의 ref: 'master' 하드코딩(403행). 기능 자체(추가/편집/중복 ID 검증/SHA 충돌 처리)는 잘 동작하는 수준.
  • workflows 운영 — pip install yfinance pandas 버전 미고정(yfinance는 파괴적 변경이 잦은 대표적 패키지), concurrency 그룹 없음(일별 작업과 30분 작업이 겹치면 push 충돌로 실패 가능), push 실패 시 재시도/rebase 없음, pip 캐시 미사용.
  • analysis/ 양호 — 방법론 문서화가 충실하고 가정이 명시적. 다만 대시보드와 연결되지 않은 채 data.js 포맷에 직접 의존하므로, Phase 1 데이터 포맷 개편 시 함께 마이그레이션 필요.

C2 — 42.5MB 초기 페이로드 (상세)

data.js는 indent=2로 직렬화되어 42.5MB이며(콤팩트 직렬화 시 25.9MB — 16.5MB가 공백), 프런트는 data.js?t=Date.now()로 로드해 브라우저/CDN 캐시를 완전히 무효화합니다. gzip 전송을 감안해도 방문마다 수 MB를 받고, 모바일에서는 JSON 파싱만으로도 수 초가 걸립니다. 281,349개 포인트의 레코드형 JSON은 키 문자열 반복만 십수 MB입니다.

  • 즉효(반나절): json.dumps(..., separators=(",", ":")) — 42.5→25.9MB(−39%). 캐시버스터를 Date.now() 대신 일별 버전 문자열로.
  • 근본(Phase 1): "메타+현재가" 소형 파일과 pair별 히스토리 파일 분리 + 컬럼형 배열({dates:[], common:[], preferred:[]}) — 초기 로드는 수백 KB, 선택 종목만 지연 로드. 부록 8.2 스키마 참고.

H4 — 지수 산정 방식 불일치 (상세)

일별 배치(data.js)의 "괴리율 지수"는 발행사 sqrt 우선주 시총 가중이고 비중 모달의 설명도 그렇게 안내합니다. 그러나 장중에는 applyCurrentSnapshot이 current.json의 averageSpread (= build_summary의 대표종목 단순평균)를 지수 카드 값으로 덮어쓰고(index.html:4734~4743), 같은 값을 지수 pair의 히스토리에 upsertHistoryPoint로 기록합니다(4746~4750행). 즉 당일 지수 포인트는 단순평균, 익일 배치 후에는 sqrt 가중으로 바뀌는 비일관 상태입니다. 프런트에 이미 sqrt 지수 실시간 계산기(calculateSqrtPreferredMarketCapSpreadIndex)가 있으므로, current.json의 단순평균보다 이를 우선 사용하거나, fetch_current.py가 동일 가중 방식을 계산해 내려주는 식으로 단일화해야 합니다.

7.holding_value 프로젝트 진행 방식 권고

결론: 별도 세션에서 진행하는 것이 맞습니다. 단, 목적에 따라 세션 구성이 달라집니다.

  • 현재 세션의 제약: 이 세션은 ducklove/common_preferred_spread 저장소에만 접근하도록 스코프되어 있고, 다른 저장소를 세션에 추가하는 도구도 이 세션에는 활성화되어 있지 않습니다. 따라서 holding_value 코드를 여기서 직접 읽거나 수정할 수 없습니다.
  • 케이스 A — holding_value 자체의 리뷰/리팩토링: holding_value 저장소로 새 세션을 시작하세요. 이 보고서를 그대로 템플릿(평가 축: 데이터 무결성/페이로드/모놀리스/중복 구현/운영 안전망)으로 재사용하면 같은 깊이의 리뷰를 훨씬 빠르게 받을 수 있습니다. 아키텍처가 비슷하다면 C1·C2·H5 류의 문제가 동일하게 존재할 가능성이 높으니 그 항목부터 점검을 요청하는 것을 권합니다.
  • 케이스 B — 두 프로젝트의 공통 모듈 추출: UI/차트/스냅샷 병합 로직을 공유 라이브러리로 뽑아내는 작업이라면, 새 세션을 만들 때 두 저장소를 함께 연결해 시작하는 것이 좋습니다 (한쪽만 보면서 추상화하면 다른 쪽에 맞지 않는 인터페이스가 나오기 쉽습니다). 공유 방식은 ① 별도 저장소 + 양쪽에서 복사 동기화(가장 단순), ② git submodule, ③ npm 패키지(빌드 도입 후) 순으로 검토하면 됩니다.
  • 권장 순서: 이 프로젝트의 Phase 0~2를 먼저 끝내고 → 그 결과(모듈 경계, 데이터 스키마)를 기준 삼아 holding_value를 같은 구조로 정리 → 마지막에 공통 모듈 추출. 추상화는 두 번째 사용처가 생겼을 때 하는 것이 가장 정확합니다.

8.3 워크플로우 보강 예시 (Phase 0)

# 두 워크플로우 공통
concurrency:
  group: data-commit          # 일별/30분 작업의 push 경합 방지
  cancel-in-progress: false

- name: Install dependencies
  run: pip install -r requirements.txt   # 버전 고정

- name: Backup previous data            # 덮어쓰기 전 보존
  uses: actions/upload-artifact@v4
  with: { name: data-backup-${{ github.run_id }}, path: data.js, retention-days: 90 }

- name: Commit and push if changed
  run: |
    ...
    git pull --rebase origin master && git push   # 경합 시 재시도

본 보고서는 2026-06-10 기준 master 최신 커밋(2560d19)을 대상으로 전체 소스를 정독·검증하여 작성되었습니다. 수치(파일 크기, 포인트 수, 유실 구간)는 모두 저장소 내 실데이터에서 직접 측정한 값입니다.
